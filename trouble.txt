站点故障排查手册（trouble.txt）
================================================================================
用途：记录 extremalmath.github.io 维护过程中常见故障的症状、原因与解法，
      供后续维护快速查阅。
更新方法：遇新故障并解决后，于文末「更新记录」追加一条（日期 + 现象 + 解法），
      保持本手册持续累积。
维护规则（记录生命周期）
--------------------------------------------------------------------------------
一、适用范围
  本规则适用于本手册中除「长期约定」类记录（见第七款豁免清单）以外的全部故障记录。
  本维护规则本身不受退役条件约束，永久保留。

二、记录字段
  每条故障记录须标注「首次记录日期」（格式 YYYY-MM-DD），作为计时与溯源基准。
  既有记录统一按 2026-10-17 补录该字段。

三、术语定义
  1. 调用（触发）：指在每个自然日复盘时，依据既有记录判定同类故障是否再次出现；
     若同类故障再次出现，则该记录视为「已调用 / 已触发」。
  2. 静默日：指一个完整的自然日内该记录未被触发（即无同类故障再现）。
  3. 退役：指将某条故障记录从本手册中删除，并于「更新记录」留痕
     「已退役 <编号> <标题>（静默天数）」。

四、计时规则
  1. 每条记录独立计时，互不影响。
  2. 记录的「静默天数」初始为 0，自其首次记录日期起算；每次触发后归零，
     并自触发当日起重新累计（计时基准前移至最近一次触发日）。
  3. 每当一个完整的自然日结束时，若该记录当日未被触发，则静默天数 +1；
     若该记录当日被触发，则静默天数归零，并自触发当日起重新累计。
  4. 计时以运行本手册维护任务的设备本地自然日为准。

五、退役条件与流程
  1. 当某条记录的静默天数达到 300 日，即进入退役候选。
  2. 退役评估于每次维护会话开始时由 agent 执行。
  3. 候选记录的退役须先生成待办事项，经用户确认后方可执行；未经确认不得删除。
  4. 执行退役前，须检索并清理本手册各节及全站引用页面中对该记录的全部引用，
     消除断链后方可删除。
  5. 退役时于「更新记录」留痕「已退役 <编号> <标题>（静默天数）」。

六、评估与确认
  本规则为长期约定。退役评估依第五款自动执行，但单次退役动作仍须按第五款第 3 项
  取得用户确认，不视为「逐次重复授权」。

七、豁免清单
  下列「长期约定」类记录不纳入退役计划，永久保留（清单可依实际情况增补）：
  - 二、3　发布后改名禁忌（依据 style-guide.txt 规定）

一、链接类故障
================================================================================

1.1 死链：href/src 指向不存在的文件
    首次记录日期：2026-10-17
    症状：页面打开后点击链接 404；check_links.py 报 BROKEN LINKS。
    原因：文件未推送/被删/移动/改名，或相对路径写错（如 ../ 层数不对）。
    解决：① 运行 .workbuddy/check_links.py 定位；② 确认目标文件在本地存在；
          ③ 若文件在本地但不在远端（selfcheck.py 的 local-only 列表），
             与引用它的页面同批推送（push-rules 明禁链接先于文件上线）。

1.2 改名断链：文件已改名，页面仍引用旧名
    首次记录日期：2026-10-17
    症状：改名后原链接 404；本地 check_links 报错。
    原因：改名与改引用未同轮完成（今日实例：Evans PDF 改名后 books.html
          一度不同步，靠全站 grep + check_links 抓到）。
    解决：改名后立即全站搜索旧名（Grep 工具或 grep -rn "旧名" --include="*.html"），
          把所有引用改到新名，再跑 check_links.py 确认 0 失效。
    预防：改名前后各跑一次链接检查；改名只改未被推送过的文件（见 2.3）。

1.3 中文/空格文件名的编码死链
    首次记录日期：2026-10-17
    症状：链接在本地正常、线上 404；或反过来。
    原因：URL 中空格须编码为 %20、中文须编码为 %E4%B8%AD 形式；浏览器地址栏
          与 href 属性行为不一致；不同服务器/工具对未编码字符处理不同。
    解决（优先）：把文件改名为纯 ASCII 小写下划线名（如 evans_pde_2nd_ed.pdf），
          页面引用同步改——这是今日实际采用方案，彻底消除编码风险。
    解决（必须保留中文名时）：href 用百分号编码；check_links.py 已内置
          urllib.parse.unquote 解码，可正确识别。
    教训：新文件入库时直接按 ASCII 命名，不要留到推送前才处理。

1.4 推送顺序造成的线上死链
    首次记录日期：2026-10-17
    症状：页面推送后线上点击 404，过段时间又正常（文件后补）；
          或窗口期内用户遇到死链。
    解决：引用文件的页面与文件本身放同一批推送；PDF 等大文件先传 blob 占位，
          再与页面同批 commit。

1.5 根绝对路径被误判为死链（check_links.py 误报）
    首次记录日期：2026-10-18
    症状：404.html 改用站点根绝对路径（href="/migrations.html"、
          href="/index.html"、href="/nownow/now.html"）后，check_links.py
          报 BROKEN LINKS（resolves to: ..\..\migrations.html 等）。
    原因：检查器把以 "/" 开头的网站根绝对路径当成相对路径解析；Windows 下
          os.path.join(ROOT, "/x") 返回 "D:/x"（保留盘符、丢弃目录），
          指向站点根之外，故判为失效。实为 GitHub Pages 根 "/" 部署下的正确写法，
          线上访问返回 200。
    解决：check_links.py 增加 pathpart.startswith('/') 分支——去掉前导斜杠后
          以 ROOT 为基准解析（os.path.join(ROOT, pathpart.lstrip('/'))），
          再判断 exists。改后 404.html 的 3 个根绝对链接正确通过"0 失效"校验。
    教训：根 404.html 会被返回给任意深度 URL，其链接必须用站点根绝对路径（/ 开头）；
          此写法会让朴素相对链接检查器误报，检查器需显式支持根绝对路径解析。

二、文件名类故障
================================================================================

2.1 双扩展名（如 GTM_244_Bondy_Murty_Graph_Theory.pdf.pdf）
    首次记录日期：2026-10-17
    影响：功能正常，但不专业、易误判为重复文件。
    处理原则：已上线的文件不改名（见 2.3），记录备查即可；未上线的新文件
          入库时发现双扩展名应直接改单扩展名。

2.2 大小写混淆
    首次记录日期：2026-10-17
    风险：Windows 本地不区分大小写，GitHub Pages（Linux）区分。
          本地 LinkChecker 通过、线上 404 的典型原因之一。
    预防：全站文件名一律小写（现有 evans_pde_2nd_ed.pdf 等即此风格）；
          检查时以 check_links.py 在本地的大小写敏感解析为准。

2.3 发布后改名禁忌（style-guide.txt 规定）
    首次记录日期：2026-10-17
    原则：文件名一旦发布到线上就不再改名——旧 URL 会 404，外链/收藏全断。
    变通：确需改名时，保留旧文件或做跳转页；本次 Evans 改名发生在推送前，
          属于安全窗口，改名后已全站同步。

三、推送类故障（Git Data API）
================================================================================

3.1 代理/出口拦截
    首次记录日期：2026-10-17
    症状：git push / git fetch 稍大传输即被 reset 或 unpack-objects 超时；
          "unpack-objects failed"。
    原因：本机 git 全局配置 http.proxy=127.0.0.1:7890（用户代理常未运行）；
          WorkBuddy 沙箱内部代理对 GitHub 无效。
    解法：① 小请求（API/ls-remote）用环境变量绕行直连：
          env -u http_proxy -u https_proxy -u HTTP_PROXY -u HTTPS_PROXY \
              -u all_proxy -u no_proxy <命令>
          ② 大流量一律走 GitHub REST/Git Data API，只传差异文件。

3.2 Git Data API 422 "Invalid tree info"
    首次记录日期：2026-10-17（2026-10-21 补充第二种根因）
    症状：POST /git/trees 返回 422 Invalid tree info。
    两种独立根因（均会报同一 422，需分别排查）：
      a) 请求体字段名用错——必须是 "tree"，不是 "entries"（2026-10-17 踩坑）。
      b) tree 数组为空——无变更时仍提交空 entries，GitHub 要求至少一条有效条目
         （2026-10-21 踩坑，见 11.8）。
    解法：POST https://api.github.com/repos/{owner}/{repo}/git/trees
          body = {"tree": [ {...}, ... ], "base_tree": "..." }
          且构造 entries 前先判空，无变更直接返回（push_site.py 已加守卫）。
    教训：此错误已踩过两次、根因不同；写推送脚本时先核对字段名，再判空。

3.3 大文件上传（PDF 动辄 10MB+）
    首次记录日期：2026-10-17
    流程：POST /git/blobs（base64 内容）→ POST /git/trees → POST /git/commits
          → PATCH /git/refs/heads/main（force=False，只允许 fast-forward）。
    要点：① 一个文件一个 blob，失败只重传该文件；② 每步检查返回码与 sha；
          ③ 21.6MB 级批次（如三本 PDF）已验证可成，仍建议分批+逐步验证；
          ④ 推送后跑 selfcheck.py 对比本地/远端 sha，确认落地。

3.4 token 权限
    首次记录日期：2026-10-17
    教训：fine-grained token 对仓库 API 报 403；用 classic token（ghp_ 开头，
          repo+workflow 权限）。token 存于本地维护配置文件（不入库、不公开）。
    注意：token 不写进任何会推送的文件；.workbuddy/ 与配置文件不推送。

6.1 aleph 占位符（ℵ）不变成图片
    首次记录日期：2026-10-17
    先判别：picture/<data-pic>.png|jpg|jpeg|webp 都不存在时保持 ℵ 是设计行为，
          不是故障。放入图片后下次打开自动替换，无需改页面。
    真故障排查：① 浏览器 Console 看 picture.js 是否加载（200？）；
          ② data-pic 路径是否与文件位置一致（注意 private/ 层级）；
          ③ 页面是否漏写 <script src="picture.js">。

6.2 JS 错误导致页面空白/不渲染
    首次记录日期：2026-10-17
    工具：node --check <file> 过语法；浏览器 Console 看运行时错误。
    高发点：updates.js 条目字符串内嵌双引号须转义 \"；
          now.html 等页面对已删除 DOM 的引用要有 null 判断。

6.3 本地正常、线上异常
    首次记录日期：2026-10-17
    顺序排查：① 文件是否真的推送了（selfcheck.py 的 local-only 列表）；
          ② 是否 CDN 缓存（见 4.1）；③ 文件名大小写（见 2.2）。

6.4 CV 三页页脚「更新日期」不一致
    首次记录日期：2026-10-17
    错误所在网页：cv-pdf-generator/cv.html、cv-pdf-generator/cv-zh.html、cv-pdf-generator/cv-en.html
    错误描述：cv-en.html 显示「Last updated October 2026」；cv-zh.html 与 cv.html
              无任何更新日期/页脚，三页不一致；且「October 2026」格式与站点标准
              「Last updated Oct 17, 2026」（短月份 + 日）不符。
    严重程度：低
    解决方案：统一三页页脚——cv-en.html 改为 "Last updated Oct 17, 2026"；
              cv-zh.html 补 "Last updated Oct 17, 2026"；cv.html 补
              "© 2026 ExtremalMath · Last updated Oct 17, 2026"（或维持精简并注明
              有意省略）。改后跑 check_links.py 确认无影响。

6.5 CV 中文版姓名未中译（Yuanbo Li → 李元博）
    首次记录日期：2026-10-17
    症状：中文简历页眉与简介仍显示英文名 "Yuanbo Li"，与中文版整体语言不符（语言混乱）。
    原因：extractBasic 抽取 .hero-info h1 后未走 t() 翻译，姓名恒定英文；
          词典（TERMS）缺 "Yuanbo Li → 李元博"；BIO_ZH 硬编码英文名。
    解决：① TERMS 加 ['Yuanbo Li', '李元博'] 与 ['Li Yuanbo', '李元博']（gi 不区分
          大小写，覆盖「名+姓」「姓+名」及大小写变体，统一译为「李元博」）；
          ② extractBasic 姓名改走 t()；③ BIO_ZH 改「我是李元博（Bruce Lee）…」。
          已 node --check + test_cv_e2e 验证（zh 输出含「李元博」且不再出现 Yuanbo）。

二、遇到的问题、改进方法与实际效果
--------------------------------------------------------------------------------
【问题 1】404.html 内 File Migration Log / Back to Home / now 链接失效。
  现象：访客从旧 PDF 链接（如 /notes/old.pdf）进入自定义 404 后，点击链接二次 404。
  根因：GitHub Pages 的自定义 404.html 会被返回给任意未命中 URL，浏览器地址栏
        仍停留在该深层路径；404.html 使用相对链接（href="migrations.html"）被解析
        成 /notes/migrations.html，文件不存在。目标文件本身均存在。
  改进：将 404.html 全部链接改为站点根绝对路径（/index.html、/migrations.html、
        /nownow/now.html），页脚日期同步 Oct 18。
  效果：线上穿透验证 404.html HTTP 200 且含根绝对链接，点击可从任意深度正确跳转；
        旧 PDF 路径仍按预期 404 并引导至迁移日志。

【问题 2】check_links.py 将根绝对路径误判为死链。
  现象：改完 404.html 后自检报 4 处 BROKEN LINKS（resolves to: ..\..\...）。
  根因：检查器把以 "/" 开头的网站根绝对路径当相对路径解析；Windows 下
        os.path.join(ROOT, "/x") 返回 "D:/x"（保留盘符、丢弃目录），指向站点根外。
  改进：check_links.py 增加 pathpart.startswith('/') 分支，去掉前导斜杠后以 ROOT
        为基准解析再判断 exists。
  效果：复跑 0 失效，自检重新可用；该坑已固化为 trouble 1.5 防复发。

【问题 3】已上线 PDF 改名后旧 URL 必须 301（前期阻塞）。
  现象：改名即删旧路径→旧 URL 404，违反当时的"旧 URL 不得 404 / 须 301"约束，
        推送被阻塞。
  根因：经 WebSearch 多源核实，GitHub Pages 无服务端 301 能力（无 _redirects/
        .htaccess/反代；jekyll-redirect-from 仅 meta-refresh 200 页且对 .pdf 受限）。
  改进：先备 Netlify 方案（A，仓库根加 _redirects/netlify.toml）供决策；用户最终
        反转决策，放弃 301、接受旧 URL 直接 404，撤销相关硬编码约束。
  效果：阻塞解除，改名+结构整改完整变更集成功上线（commit 5e7d58c1）。

【问题 4】updates.js 条目冗余。
  现象：2026-10-18 两条公告合计超 100 词且含已被否决的"301 待配置"陈旧表述。
  改进：合并为一条 ≤100 词核心摘要，并删除过时 301 措辞。
  效果：公告简洁、口径与线上状态一致。

三、关键问题复盘：更优 / 更高效方案对比
--------------------------------------------------------------------------------
【复盘 A】404 页链接失效的预防
  已用方案：事后发现失效 → 改为根绝对路径（最快止血）。
  备选 1：在 404.html 加 <base href="/">，使页面内所有相对链接自动基于根解析。
          优：改动极小、一次性解决所有相对引用；缺：base 会影响全页相对引用（本页
          无其他相对资源，安全），且可读性略降、易与个别需相对解析的链接冲突。
  备选 2：把"404 页禁用相对链接、强制根绝对"写入 push-rules/style-guide 作为前置
          检查规则，提交前即拦截。
          优：预防性强、杜绝返工；缺：需额外流程/工具支撑。
  对比结论：根绝对路径直接改是当前最优（稳健且零新增依赖）；若能早一步把该约束
          写入规范，可省去本次返工与二次推送。建议在 push-rules 一.4 或四 增补一条
          "404.html 链接须为根绝对路径"。

【复盘 B】链接检查器对根绝对路径的误报
  已用方案：发现误报 → 特判 "/" 开头（本次已落地，效果 0 失效）。
  更优：让检查器默认以站点根为基准解析 "/" 开头路径（本次即此做法），并可扩展支持
        自定义 <base>。优：一次修复长期受益、无显著劣势；缺：需维护解析逻辑。
  对比结论：本次修复即最优解，已记入 trouble 1.5，无需再投资。

【复盘 C】301 阻塞的决策效率
  已用方案：先备 Netlify 方案（A）呈现选项 → 用户反转接受 404。
  更优：在投入 Netlify 准备（建 _redirects/netlify.toml 后又删除）之前，先一步用
        WebSearch 确认"GitHub Pages 是否支持服务端 301"。
          优：早核实可省去 A 方案的创建/删除往返，提效明显；
          缺：用户决策本身需要选项呈现，准备 A 也帮助用户直观评估"迁平台成本"，
              不完全是浪费。
  对比结论：把"平台能力可行性"列为改名/迁移类任务的第一步核查，写入标准流程可提效；
          但保留"选项呈现"仍有沟通价值。

【复盘 D】整体推送与验证流程
  已用方案：Git Data API 增量（push_site.py）+ 手动 dry-run + 线上 ?cb= 穿透验证。
  更优（历史建议⑤）：push_site.py 末尾自动轮询 pages/builds/latest 至 built +
        关键页自动穿透 200，把"初查 MISS 勿误判"自动化。
          优：省手工等待、防误判、可重复；缺：需写脚本（约 20 行）。
  对比结论：当前手工流程已可行且可靠；建议将自动轮询+穿透固化为 push_site.py 收尾
          步骤，作为长期提效项（非紧急）。

【总体结论】
  今日主线（改名迁移上线 + 公告 + 404 修复）已闭环，两次推送（5e7d58c1、eac1793）
  均验证通过。最值得固化的两点提效：① 404.html 链接强制根绝对（写入规范防返工）；
  ② push_site.py 收尾自动轮询 Pages built + 穿透验证。其余改进（检查器根绝对解析）
  已就地修复并留档。

11.1 png-to-ico 库与 sharp 输出的 PNG 格式不兼容
    首次记录日期：2026-10-21
    症状：调用 png-to-ico 的 imagesToIco 处理 sharp 生成的 PNG 时抛
          "Cannot read properties of undefined (reading 'length')"，无法生成 ICO。
    根因：该库对 PNG 的 IHDR/chunk 布局有隐性假设，与 sharp 输出不完全一致；
          属于库自身对输入格式过于挑剔，非调用方错误。
    当前处理：放弃第三方库，手写 PNG-in-ICO 编码器——ICONDIR（6 字节）+
          6 条 ICONDIRENTRY（每条 16 字节）+ 数据偏移，256px 尺寸按规范编码为 0。
    反思与改进建议：
      ① 优先选成熟、输入宽容的库（如 icotool 命令行或 node-ico），并对输入做
        PNG 规范化（sharp 重编码一次）再喂给编码器，而不是手写二进制协议。
        手写编码器虽可控，但每多一种尺寸/色深就要补一条分支，长期维护成本高。
      ② 若必须手写，应写单元测试覆盖 ICONDIR/ICONDIRENTRY/偏移三处，
        并用 ico 解析库反向读回校验，而非只靠浏览器能显示。
      ③ 记录到本手册前应先确认该库是否已被替代——避免后来人重踩。

11.2 16px favicon 可读性（4 轮设计迭代才定稿）
    首次记录日期：2026-10-21
    症状：第 1 版 Arial 文本 glyph 16px 下笔画糊成一团；第 2 版几何描边因
          sub-pixel 抗锯齿仍模糊；第 3 版填充 A + 中横镂空，16px 下镂空塌陷成 blob；
          仅第 4 版（16×16 网格、实心无镂空、原生栅格化不缩放）可辨。
    根因：浏览器标签栏图标实际渲染尺寸只有 16×16 像素，任何小于 2px 的描边、
          镂空或负空间都会因抗锯齿被吞掉；以"大屏清晰"为设计目标会直接导致
          favicon 不可用。
    当前处理：定稿为实心无镂空 Aleph，每个尺寸都从同一矢量定义独立栅格化，
          不做缩放；颜色用全站 accent #8c2f39。
    反思与改进建议：
      ① favicon 的设计约束应从 16px 出发逆向推导，而非从大图缩小——这是
        本类问题的通用原则：先画 16px 位图，再反推矢量，而不是反过来。
      ② 迭代过程应保留各版截图（按尺寸归档），否则下次换图形时又要重走 4 轮。
        建议把 icon_assets_try/ 下的各版截图作为设计资产保留（本地、不推送）。
      ③ 若日后换图形，应先在 16px 下验证可辨性，再谈美学。

11.3 插入脚本的根目录路径前缀 bug
    首次记录日期：2026-10-21
    症状：给根目录 HTML 插入 favicon 链接时生成 "../picture/favicon.ico"，
          check_links.py 报失效链接。
    根因：用 os.path.dirname(relpath) 计算前缀，对根目录文件（relpath="index.html"）
          返回空字符串 ""，拼接后变成 "../picture/…"。空字符串在路径拼接中
          不会被当作"当前目录"。
    当前处理：修正为根目录直写 "picture/…"，子目录用 "../picture/…"，
          两层用 "../../picture/…"；复跑 check_links.py 0 失效。
    反思与改进建议：
      ① 路径前缀计算应统一用 pathlib 或 os.path.relpath(target, dir) 的
        正向推导，而非 dirname 的反向推导——后者天然有根目录边界缺陷。
      ② 此类"边界值"（根目录、单层、多层）应作为插入脚本的必测用例，
        在脚本内自测三个层级，而不是靠 check_links 事后抓。

11.4 页脚日期格式被误判为例外
    首次记录日期：2026-10-21

11.5 migrations.html 桌面端表格溢出

11.6 沙箱出口封锁导致站点可达性误判（MathOverflow 红色报错）
    首次记录日期：2026-10-21
    症状：本沙箱内 HEAD/GET mathoverflow.net 均返回 HTTP 403，
          stackexchange.com / math.stackexchange.com / stackoverflow.com 同理，
          故标注红色"Unreachable"异常；但用户反馈 MathOverflow 实际可访问。
    根因：沙箱对 Stack Exchange 网络有出口封锁（403），与站点本身状态无关。
          我把"沙箱内探测失败"等价于"站点不可达"，属于环境混淆。
    当前处理：按用户要求清空 note 字段，不再渲染红色 alert；并在 note 原文中
          保留了 "the site itself is reachable" 的说明（后随 note 一并移除）。
    反思与改进建议：
      ① 可达性验证的结果必须标注探测来源——"本沙箱内 403"与"站点宕机"是两件
        事。更健壮的做法：note 字段存两段（probe: 沙箱结果 / verdict: 判定），
        渲染时只在 verdict 为"确认站点故障"时才标红，沙箱限制改为灰色注释。
      ② 当沙箱探测与用户实际体验冲突时，应以用户为准、以沙箱为参考，
        并在条目旁标注"沙箱内无法验证"而非断言故障——避免误导访客。
      ③ 建议建立一个白名单域名列表，对已知被沙箱封锁的域名跳过探测或
        直接标记"未验证"，减少往返。

11.7 本地 git 历史与远端主线分歧，GAU 推送失败
    首次记录日期：2026-10-21
    症状：auto_upload.py sync 能 commit（本地新增 81779be）但 push 失败——
          git 线协议被代理拦截（Failed to connect to github.com:443 over proxy
          127.0.0.1），Git Data API fallback 也未成功。
    根因：本地 git 仓库是 10-18 push_site.py 自建的单提交历史（49b8143，
          仅 1 个 commit、无远端分支引用），而 push_site.py 走 Git Data API
          直接更新远端 ref，两者从未同步——本地 HEAD 与远端 HEAD 是两条独立历史。
          API fallback 要求本地历史能基于远端 tip 重写，因分歧而拒绝。
    当前处理：页面本身已由 push_site.py 推送上线（commit eee4c0fe，Pages built），
          不受影响；本地未推送的 commit 含 push_site.py 的空变更守卫修复。
    反思与改进建议：
      ① 根本解法：让 push_site.py 也走 git 线协议（或反之），统一单一真相源。
        当前两套机制并存是最大的结构性风险——同一文件可能被两个渠道各写一次。
      ② 若保留双通道，应在每次推送后同步本地 git（git fetch origin &&
        git reset --hard origin/main），使本地 HEAD 始终对齐远端，
        这样 GAU 的 fallback 才能工作。
      ③ 更彻底的方案：废弃 push_site.py，全面改用 GAU（其 doctor 已确认
        api.github.com 可达、push_mode=auto），只在 git 线协议可用时走 git。
        这样不存在两套历史，且 GAU 有 secret scan 等安全机制。
      ④ 当前不影响线上页面，但本地 git 的 "chore: update 3 files" commit
        若后续用 git push 会覆盖远端——须先 rebase 或 reset 对齐。

11.8 push_site.py 缺少空变更守卫，触发 422 "Invalid tree info"
    首次记录日期：2026-10-21
    症状：当 ADD/MODIFY/DELETE 均为 0 时，POST /git/trees 返回
          422 {"message":"Invalid tree info"}。
    根因：无变更时仍向 GitHub 提交空的 tree 数组；GitHub 要求 tree 至少含
          一条有效条目（或至少 base_tree 合法且 entries 非空）。
          注意此 422 与 3.2 的字段名错误（"entries" vs "tree"）是两种不同根因。
    当前处理：在 entries 构造前加守卫——无变更时直接打印 "No changes" 返回。
    反思与改进建议：
      ① 此守卫应放在 dry-run 阶段之前，让 dry-run 也能给出 "No changes" 而非
        空列表，减少误操作空间。
      ② 更完整的设计：push 脚本应区分"无变更"、"仅排除文件变更"、"有真实变更"
        三种状态并给出不同提示，而不是把空 tree 交给 GitHub 去拒绝。
      ③ 该 422 已在 3.2 记录过一次字段名误用，建议 3.2 标题细化为
        "3.2 Git Data API 422（字段名误用 / 空 tree）"，把两种根因并列，
        避免后来人只记一种。

11.9 .text-hover 的 skewX 作用域选型（布局破坏风险）
    首次记录日期：2026-10-21
    风险：若把 skewX(-10deg) 直接加到 .res-row（flex 容器）上，整行倾斜会
          改变 flex 布局的占位盒，导致相邻行错位、border 线偏移；
          若加到 display: block 的元素上，skew 会撑大元素盒模型。
    当前处理：skew 只作用于 .text-hover（display: inline → hover 时
          display: inline-block），包裹在 name/sub/alert 内部；flex 行本身
          只变颜色，不变形。同时保留 prefers-reduced-motion 禁用过渡。
    反思与改进建议：
      ① 此选型正确，但应写成注释固化（已做），否则下次改样式容易误把
        transform 提升到父级。
      ② 更安全的写法是给 .text-hover 加 will-change: transform, color，
        让浏览器提前合成层，避免 hover 时重排闪烁（当前 0.2s 下不明显，
        但条目多时可能出现）。
      ③ skewX(-10deg) 在长文本上会让末端偏移约 17% 行高，若某行描述特别长
        可能与右侧 alert 重叠；当前 max-width: 45% 的 alert-wrap 留出了余量，
        但应作为已知边界记录——若将来描述长度不设上限，需改用 font-style: italic
        的降级方案。
