条目 1 · 脚本引用路径错误导致简历完全不生成
================================================================================
问题现象
  cv-zh.html / cv-en.html 打开后没有任何反应，也不报错，控制台提示 CVGenerator
  未定义。抓取、翻译、渲染全部不执行。

原因定位
  两个页面的 <script src="../cv-generator.js"> 多写了一层 "../"。
  cv-generator.js 与这两个页面同在 cv-pdf-generator/ 目录内，同目录引用不应
  带 "../"。（最初把文件从根目录移入本文件夹时，只改了 cv.html 与 about.html
  的引用，漏改了这两个后建的页面。）
  注意：fetchPages 里的 "../about.html"、"../talks/talks.html" 是【正确】的，
  因为源页面确实在上一层的站点根目录 —— 不要把两者一起改掉。

解决方案
  将两页的脚本引用改为同目录：<script src="cv-generator.js"></script>。
  fetchPages 保持不动。

后续注意事项
  · 本目录内任何页面互相引用一律用同目录相对路径；只有跨目录访问站点根目录
    的源页面时才加 "../"。
  · 移动或新建文件后，用 grep 全站扫一遍引用名，确认没有残留旧路径。
  · 死链是推送闸门（push-rules.txt 要求全站 0 失效），修复后才能推。

条目 2 · 整句词典漏译：源站改一个词，整段回退英文
================================================================================
问题现象
  在 about.html 里把某句英文稍微改一下（例如加个逗号、换个词），中文版简历
  对应位置就整段变回英文，其他句子却还是中文，看起来像"翻译时好时坏"。

原因定位
  最初 zh() 只做整句精确匹配：抽取到的整段英文必须与词典键【一字不差】才能
  命中，否则整段回退原文。在这种设计下，一份"术语表"如果是孤立单词，对整段
  抽取文本根本不会生效 —— 这是设计缺陷，不是词典不全。

解决方案
  升级为两层翻译：
    第一层 ZH（整句）：键＝英文原文整句，值＝人工审定中文。精确、零歧义，优先。
    第二层 TERMS（术语）：对未命中整句的英文自由文本，按「长词条优先」做子串
    替换。两点实现要点：
      - TERMS_SORTED 按词条长度降序排序，避免短词提前替换破坏长词匹配
        （否则 "Competition" 会先吃掉 "Mathematics Competition"）。
      - 替换用大小写不敏感的正则，并对正则元字符做转义。
  zh() 先查 ZHN，未命中才走 applyTerms()。

后续注意事项
  · 新增内容只需在两处之一追加：长句 / 简介 → ZH；专有名词 / 惯用短语 → TERMS。
    两套都在 cv-generator.js 同一文件内，不需要另建术语文档。
  · TERMS 是子串替换，存在语境误译的可能。例如 TERMS 里 Chinese → 中国，
    会把 "Chinese language" 变成"中国 language"。新增词条时要考虑是否会被
    更长的上下文误伤。
  · 术语级替换会让英文长句变成中英混排，语句可能不通顺 —— 重要条目仍应补 ZH
    整句译文。

条目 3 · 标点不一致导致查表失败、整句漏译
================================================================================
问题现象
  明明词典里有这条译文，却仍然回退成英文。逐字比对发现两边文字一样，只有
  引号和破折号的形状不同。

原因定位
  源站 HTML 里用的是弯引号 ' " 与长破折号 – —，而词典键里是直引号 ' " 与
  短横 -（多为从网页复制或手写造成）。字符串精确匹配对标点敏感，直接失配。

解决方案
  增加 norm() 归一化：把 ' ' → '、" " → "、– — → -，并据此预构建 ZHN 索引，
  使查表与录入两侧都基于归一化后的形式。

后续注意事项
  · 新增词典条目时不必纠结标点是弯是直，norm() 会处理；但仍要确认归一化函数
    覆盖了你实际使用的符号。
  · 涉及希腊字母（如 τ、≈）与数学符号时，注意源页可能是 HTML 实体
    （&tau; &asymp;），textContent 取出来才是真正的 Unicode 字符。

条目 4 · 日期字段漏译：「– 2024」在中文版裸露
================================================================================
问题现象
  中文版教育经历的高中一行显示为：– 2024高中文凭江苏省南京市第九中学
  —— 英文日期直接漏出，且与后面的中文紧贴，没有空隙。

原因定位
  ZH 词典里有 '2024 – Present'、'2024 – 2025'，唯独没有高中学历那一行的
  '– 2024'。zh() 整句未命中后转 TERMS，而 TERMS 里没有任何纯数字条目，
  于是原样返回英文。这暴露了一个盲区：字典审计若只统计"命中率"，
  会把"无需翻译的英文"（年份、技能名）与"漏译"混在一起。

解决方案
  已补 ZH 条目：'– 2024': '– 2024 年'。

后续注意事项
  · 日期类字段必须逐个核对，尤其注意「en-dash + 空格」这种组合
    （– 2024 / 2024 – Present / 2024 – 2025 形态各不相同）。
  · 做词典审计时，要人工判定每个未命中项属于"无需翻译"还是"漏译"，
    不要只看统计数字。本目录审计时的正确分类是：
    年份 2025、技能名 C / MATLAB / Java / LaTeX 属无需翻译；
    被过滤的 Course Talk 属不渲染；只有 '– 2024' 是真漏译。
  · 当前中文版仍存在日期格式不统一（2024 至今 / 2024–2025 / 2025 年 8 月
    三种风格并存），尚未统一，属已知遗留项。

条目 5 · 技能描述被整段丢弃（提取了却没渲染）
================================================================================
问题现象
  中文版「技能」一栏只有：C · MATLAB · Java · LaTeX · Python（机器学习）
  五条技能描述全部消失，尽管它们已被正确提取、也已翻译成中文。

原因定位
  extractSkills() 返回的是 { name, desc }，desc 已完成翻译；但渲染层写成
  d.skills.map(s => s.name).join(' · ')，【只取 name】，desc 被丢弃。
  也就是说翻译工作真实发生了，只是结果从未被输出 —— 这类 bug 最隐蔽，
  因为翻译覆盖率检查是"全绿"的。

解决方案
  改为每项独立成行，并在 desc 存在时拼接：
    s.name + (s.desc ? ' — ' + s.desc : '')
  复用既有的 .cv-desc 块级样式，多行自然纵向堆叠。

后续注意事项
  · 数据层返回的字段，必须与渲染层实际使用的字段逐一对照。改数据结构时，
    先 grep 该字段的全部消费点再动手。
  · 写测试时，"断言内容存在"不足以发现这类问题；必须为【每一个本该出现
    却没出现】的字段单独写断言（当时为 5 条技能描述各写了断言）。
  · 空值保护：desc 可能为空（源页缺该子元素），拼接必须有 s.desc ? 判断，
    否则会留下悬空的分隔符。

条目 6 · 研究兴趣描述在数据层被丢弃（比条目 5 更深）
================================================================================
问题现象
  中文版「研究兴趣」只有"极值图论"四个字，后面那段已经翻译好的完整描述
  （H-自由图、Turán 型极值问题等）完全不出现。

原因定位
  问题出在 assemble() 而非渲染层：
    interests = cards.filter(c => !c.status).map(c => c.title)
  这里在上游就把 title 之外的字段丢掉了，渲染层 join('； ') 再怎么改也
  无法补救。修复条目 5 时若只盯着渲染层，就会漏掉这一处。

解决方案
  interests 改为保留 desc 的对象数组 [{ title, desc }]；渲染层每项独立成行，
  分隔符按语言取全角「：」或半角": "。

后续注意事项
  · 【修复要在最深的截断点】。发现"内容没显示"时，先确认是数据层丢的还是
    渲染层丢的，再动手，否则容易修错层。
  · interests 的数据结构变更属于破坏性改动：改前必须 grep 确认唯一消费点
    （当时确认 d.interests 只在渲染处用到，works / notes 不受影响）。

条目 7 · 双语标签 service 定义了却从不显示
================================================================================
问题现象
  讲解员、志愿支教老师、志愿者三段经历直接排在"技能"之后，没有任何小标题，
  读者看不出这几项属于什么类别。

原因定位
  LABELS 里 zh.service = '学术服务与社会实践'、en.service = 'Service & Outreach'
  都已写好，但渲染代码在遍历 d.service 之前忘了输出对应的二级标题，
  导致这两个键的使用次数为 0 —— 标签存在但从未被消费。

解决方案
  在服务循环前补一行：<div class="cv-sub2"> + esc(lab.service) + </div>。

后续注意事项
  · 双语标签表（LABELS）要定期做"键使用率"审计：逐个键 grep 引用次数，
    0 次即为死配置。本目录审计结果见条目 8。
  · 新增 LABELS 键时，同一轮就要把它接到渲染层，否则会重蹈覆辙。

条目 8 · 死配置 langName
================================================================================
问题现象
  LABELS.langName（zh: '中文' / en: 'English'）在全文件没有任何引用。

原因定位
  该键是早期预留的"语言名称"字段，但简历的语言已由 <html lang="zh"> 与页面
  <title>学术简历（中文）</title> 表达，页面上再显示一次语言名属于重复信息，
  最终从未被使用。

解决方案
  两个语言版本中的该键一并删除。

后续注意事项
  · 配置项若长期没有消费点，就是负债而非扩展点，应删除而不是留着"以后可能
    用"。若将来确实要在简历上标注语言，重新加回即可，成本极低。
  · 与条目 7 相反的判断标准：service 有明确的展示价值（补上即修复缺陷），
    langName 没有；区别在于"是否解决了一个实际的展示缺口"。

条目 9 · 页脚日期用 UTC 且格式过细
================================================================================
问题现象
  两个问题同时存在：
    (1) 页脚显示 2026-10-17，比同页的 "Last updated Oct 17, 2026" 更精确，
        与本站风格不一致；
    (2) 更严重的是时差 bug —— 在北京时间 00:00 至 08:00 之间生成简历时，
        日期会【少一天】。

原因定位
  旧代码：const today = new Date().toISOString().slice(0, 10);
  toISOString() 返回的是 UTC 时间，不做任何时区换算。北京时间比 UTC 快 8 小时，
  所以当地凌晨 0 点到 8 点这段时间，此刻的 UTC 日期还是"昨天"。

解决方案
  1) 改为按北京时间计算：取绝对时间戳后加固定 8 小时偏移，再读取 UTC 字段
     —— 这样得到的就是北京时间，且不受运行环境本地时区设置影响：
       const BJ_OFFSET_MS = 8 * 60 * 60 * 1000;
       function buildDate() {
         const d = new Date(Date.now() + BJ_OFFSET_MS);
         return state.lang === 'zh'
           ? d.getUTCFullYear() + '年' + (d.getUTCMonth() + 1) + '月'
           : d.toLocaleDateString('en-US', { month:'long', year:'numeric', timeZone:'UTC' });
       }
  2) 按用户选定的方案 A，只显示年+月；英文版用 toLocaleDateString 输出
     "October 2026"，中文版输出 "2026年10月"，两版各自本地化。
  3) 同步把 cv-zh.html / cv-en.html 两个页面的静态页脚改为年月。

后续注意事项
  · 【凡是"当前时间"类需求，绝不要用 toISOString()】。要么显式加时区偏移，
    要么用带 timeZone 选项的 toLocaleDateString。
  · 跨月、跨年边界必须专门测试。本模块验证时用伪造时间戳覆盖了四个边界：
      UTC 09-30 23:30 → 北京 10 月
      UTC 10-31 16:00 → 北京 11 月
      UTC 2025-12-31 16:30 → 北京 2026 年 1 月（跨年）
      英文版同步 January 2026
  · 静态页脚（写死在 HTML 里的日期）不会自动更新，需与规范同步维护。

条目 10 · 测试中出现的三类假失败（重要教训）
================================================================================
问题现象
  验证脚本多次出现断言失败，但代码本身是正确的。

原因定位
  三次失败分别对应三类不同的测试自身错误。

解决方案
  (a) jsdom 模拟的 DOM 结构与抽取选择器不匹配。
      例：伪造获奖数据时只写了 <li>文本</li>，而 extractAwards 要求
      .award-list li 内部必须有 .award-year 与 .award-text 子元素，
      结果抽出来是空字符串，看起来像"翻译失效"。
      → 造假数据前先回读抽取函数的 CSS 选择器，严格照结构构造。

  (b) 用词典里不存在的句子去期待中文译文。
      例：把 "My primary research focus is on Extremal Graph Theory, with
      H-free graph problems." 这种截断变体当作测试样本，它不在 ZH 词典中，
      回退英文才是正确行为。
      → 区分「验证翻译是否生效」与「验证内容是否渲染」两件事，各用各的样本。

  (c) 正则的 \b 对中文无效。
      例：/\b2026年10月\b/ 永远不匹配。因为 JavaScript 正则的 \w 只包含
      ASCII 字符，「月」属于非单词字符，它后面若也是非单词字符就不存在边界。
      → 含中文的断言一律用 includes 或 indexOf，不要套用英文单词边界。

后续注意事项
  · 断言失败时，先怀疑测试，再怀疑代码。本目录多次"失败"最终都定位为测试
    自身写错，而代码是对的 —— 但这需要靠回读源码来确认，不能想当然。
  · 临时验证脚本放在 managed node workspace 下，用完即删，不要留在项目里。

条目 11 · 两条触发路径的差异（架构备忘）
================================================================================
问题现象
  点击 about.html 上的按钮能生成，但直接打开 cv.html 有时抓不到内容。

原因定位
  两条触发路径的实现方式不同：
    按钮路径：generateCV({ fromCurrentPage: true })
      直接读取当前已打开页面的 DOM。始终与源同步，无联网、无跨域问题。
    超链接路径：generateCV({ fetchPages: [...] })
      需用 fetch 抓取源页面，因此要求通过 http(s) 访问（GitHub Pages 或
      本地静态服务器）。用 file:// 直接双击打开时，浏览器的本地文件协议会
      拦截 fetch。

解决方案
  两种路径都保留，按钮默认传 fromCurrentPage；cv.html / cv-zh.html /
  cv-en.html 走 fetch 并在页面上给出提示。

后续注意事项
  · 本地调试务必起一个静态服务器，不要直接双击 HTML。
  · 保持两条路径的产出内容一致，任何只改一条路径的修改都要在另一条上复测。

条目 12 · 课程作业过滤依赖显式标签
================================================================================
问题现象
  若把课程作业也写进简历，会直接违反"排除课程作业"的要求。

原因定位
  过滤靠两层显式规则，缺一不可：
    · CONFIG.excludeTalkTypes —— 按 .talk 的日期行里的类型标签精确匹配
      （如 "2026-10-10 · Course Talk" 中的 course talk）。
    · CONFIG.excludeKeywords —— 命中 homework / coursework / 课程作业 / 作业 /
      core coursework 即排除，作为兜底。
  另外 research 卡片按有无 .status 元素分流：有 status 归"作品"，无 status
  归"研究兴趣"，因此"My Teachers"下的 Core Coursework 标签天然不会进入简历。

解决方案
  以上规则已内置，无需额外操作。

后续注意事项
  · 日后新增内容若属课程作业，务必让它带上可识别的类型标签或关键词，
    否则会漏进简历。这是过滤规则唯一的失效入口。
  · talks 页当前唯一的条目恰好是 Course Talk，会被正确排除，因此简历
    "相关作品"一栏目前只有两条研究笔记 —— 这是预期结果，不是数据缺失。
